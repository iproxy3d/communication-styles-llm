# Локальная демонстрация коммуникационных стилей, Multi-Motions 28 и ассоциативной памяти

Это исполняемый пример к статье «Коммуникационные стили в агентских системах». Он показывает полный минимальный контур:

1. реальный EN/RU классификатор эмоций **Multi-Motions 28** формирует `U_t`;
2. рекуррентное состояние агента задаёт `E_t`;
3. ассоциативная эмоциональная память возвращает `A_t`;
4. из 28-мерного состояния выбирается эмоциональное поле коммуникационного стиля;
5. из SQLite берётся скрытый коммуникационный микродиалог;
6. после него добавляется мотивационный микродиалог;
7. локальная `Qwen2.5-3B-Instruct` генерирует реальный ответ.

После однократной загрузки весов внешние LLM/API для выполнения демо не нужны.

## Модели

### Эмоции пользователя

Используется опубликованная модель:

- **Hugging Face:** https://huggingface.co/proxy3d/multi-motions-28
- **описание, обучение и бенчмарки:** https://huggingface.co/spaces/proxy3d/multi-motions-28-article

`proxy3d/multi-motions-28` — XLM-R классификатор для английского и русского текста. На выходе он даёт 28 независимых sigmoid confidence scores:

```text
admiration, amusement, anger, annoyance, approval, caring,
confusion, curiosity, desire, disappointment, disapproval, disgust,
embarrassment, excitement, fear, gratitude, grief, joy, love,
nervousness, optimism, pride, realization, relief, remorse,
sadness, surprise, neutral
```

Это multi-label выход. Значения **не нормализуются до суммы 1**: несколько эмоций могут одновременно иметь высокие scores.

### Генерация ответа

Для локального ответа используется:

```text
Qwen/Qwen2.5-3B-Instruct
```

Классификатор и генеративная модель скачиваются в `demo/models/` один раз.

## Эмоциональное пространство демо

Весь коммуникационный контур использует одно и то же 28-мерное пространство эмоций Multi-Motions 28:

- `U_t` — 28 независимых sigmoid confidence scores классификатора;
- `E_t` — 28-мерное внутреннее состояние агента;
- `A_t` — 28-мерный сигнал ассоциативной памяти;
- `S_t` — 28-мерное состояние, по которому выбирается эмоциональное поле коммуникационного стиля;
- `R_t = S_t ⊙ W_character` — оценки после применения весов характера;
- SQLite содержит отдельную строку коммуникационного стиля для каждого из трёх персонажей и поля для всех 28 эмоций;
- для каждой пары `стиль × эмоция` есть три уровня интенсивности `0/1/2`;
- каждый коммуникационный вариант хранится как законченная пара `USER → ASSISTANT`.
- поле `neutral` также всегда содержит полноценный микродиалог для каждого стиля: нейтральность отключает эмоциональное усиление, но не сам коммуникационный стиль.
- мотивационные варианты также являются парами `USER → ASSISTANT`, но индексируются персонажем и уровнем; они не заменяют его регистр нейтральным текстом.

Unit-тесты используют маленький deterministic test double классификатора, поэтому для тестов не требуется скачивать веса модели.

## Три персонажа и их таблицы стиля

В базе по умолчанию есть три персонажа:

| Персонаж | Стиль | Поведение |
|---|---|---|
| **Мира** | `supportive` | тёплый, спокойный, поддерживающий; в безопасных репликах допускает мягкое кокетство |
| **Алекс** | `street` | точный и прямой, но говорит в уличном рэп/хип-хоп регистре: «бро», «чувак», «без базара» |
| **Ирис** | `ironic` | мягкая ирония и молодёжный сленг без изменения фактов и без насмешки над уязвимостью пользователя |

`communication_styles` в этом примере — не общий словарь фраз. Для каждого персонажа создана отдельная авторская библиотека: все 28 эмоций имеют свои три пары `USER → ASSISTANT` для этого персонажа. Поэтому одинаковая эмоция, например `anger`, не приводит к одной и той же подсказке у Миры, Алекса и Ирис.

Два обязательных различающихся примера:

```text
Алекс / street / anger / интенсивность 1
USER: Не тупи чувак
AI:   Ты на кого наезжаешь бро

Ирис / ironic / anger / интенсивность 1
USER: Ты совсем имба?
AI:   Тюбик, закрой свой рот
```

У Алекса и Ирис стилевые слова присутствуют в обеих ролях пар, чтобы при продолжении контекста модель видела регистр не только в ответе ассистента. У Миры пары остаются тёплыми и поддерживающими; кокетливые оттенки используются только там, где они не обесценивают уязвимость. У Ирис даже ироничные реплики не меняют факты и не высмеивают пользователя в чувствительных состояниях.

```text
Мира / supportive / fear / интенсивность 1
USER: Я боюсь, что всё пойдёт не так.
AI:   Понимаю тревогу. Давайте разберёмся по шагам, без спешки.
```

Полный набор находится в `style_demo/dialogues/mira.json`, `style_demo/dialogues/alex.json` и `style_demo/dialogues/iris.json`. `style_demo/default_styles.py` содержит только загрузчик и структурную проверку; тексты не дублируются в Python. При инициализации эти JSON-пары записываются в SQLite `communication_styles`.

Классификатор принимает английский и русский текст, но встроенные default-микродиалоги этого демо русскоязычные. Поэтому EN/RU относится к входному классификатору; полноценная англоязычная библиотека скрытых примеров в этот архив не включена.

## Эмоциональное состояние и память

Базовое коммуникационное состояние:

```text
S_base = alpha · U_t + (1 − alpha) · E_t
```

С ассоциативной памятью:

```text
S_t = alpha · U_t + (1 − alpha) · E_t + beta · A_t
```

где:

- `U_t` — 28 sigmoid scores Multi-Motions 28 для текущего сообщения;
- `E_t` — 28-мерное состояние агента перед ответом;
- `A_t` — 28-мерный агрегированный сигнал ассоциативной памяти;
- `alpha` — ориентация коммуникации на текущего собеседника;
- `beta` — сила влияния памяти.

`U_t`, `E_t` и `A_t` не являются categorical distributions: координаты Multi-Motions 28 — независимые sigmoid-оценки, поэтому их нельзя нормализовать так, чтобы сумма всех эмоций была равна единице.

В псевдокоде статьи операция `Normalize(...)` обозначает приведение результата к общей рабочей шкале. В этом demo она реализуется как покоординатное ограничение (clipping) диапазоном `[0,1]`:

```text
S_t[i] ← min(1, max(0, S_t[i]))
```

Это не `softmax`, не L1- и не L2-нормализация. При `beta=0` ограничение не меняет выпуклое смешение `U_t` и `E_t`; оно нужно как защита от выхода координаты за единицу после добавления `beta · A_t`.

Состояние агента обновляется простым учебным правилом:

```text
E_{t+1} = 0.8 · E_t + 0.2 · U_t
```

Это прозрачная учебная модель внутренней эмоциональной динамики персонажа. Вход `U_t` при этом формируется обученным классификатором Multi-Motions 28.

После ответа найденные ассоциации обновляются:

```text
A_{t+1}(q) = A_t(q) + eta · (E_t − A_t(q))
A ← gamma · A
```

В коде обновление получает именно `E_t`, то есть состояние агента перед текущим ответом, а не смешанное состояние выбора `S_t`. После EMA-обновления отдельный шаг `A ← gamma · A` применяется ко всем сохранённым ассоциациям, а каждая координата ограничивается диапазоном `[0,1]`.

`gamma` — коэффициент сохранения памяти после обновления, а не скорость обучения. В demo используется диапазон `0 < gamma ≤ 1`:

| `gamma` | Значение |
|---:|---|
| `1.0` | память не затухает; это допустимый режим без забывания |
| `0 < gamma < 1` | память постепенно забывается; чем меньше значение, тем быстрее затухание |

Параметр задаётся через `--memory-gamma` и по умолчанию равен `1.0`. Поэтому в режиме по умолчанию EMA-обновление работает, но дополнительное временное забывание отключено. Чтобы включить decay, нужно передать значение меньше `1.0`.

## Как выделяются сущности

Ассоциативная часть демонстрации намеренно реализована компактно. В SQLite хранится небольшой словарь известных сущностей, например:

```text
самолет
рейс
аэропорт
иванов
париж
билет
```

Текст нормализуется через `pymorphy3`, поэтому формы вроде:

```text
Иванову    -> иванов
Ивановым   -> иванов
самолётами -> самолет
самолёте   -> самолет
```

сводятся к одному ключу памяти. `style_demo/association.py` отделён от остальной системы, поэтому его можно заменить полноценным NER без изменения классификатора, памяти или выбора стиля.

## Что хранится в SQLite

### `communication_styles`

Три строки, по одной на каждого персонажа (`characters.style_id → communication_styles.id`), и 28 эмоциональных колонок. Строки не являются общими профилями: `Мира`, `Алекс` и `Ирис` получают разные значения даже для одной эмоции. Каждая ячейка хранит JSON с тремя уровнями интенсивности:

```text
0 -> USER + ASSISTANT
1 -> USER + ASSISTANT
2 -> USER + ASSISTANT
```

### `characters`

Имена персонажей, system prompt, связь со своей строкой `communication_styles`, `alpha`, интенсивность, уровень мотивации и начальный `E_t`. В system prompt добавлено по одному короткому словарному ориентиру регистра: например, у Алекса «бро», «чувак», «без базара», у Ирис «вайб», «жиза», «имба», «рил», «кринж». Это дополнительная страховка для генеративной модели; основным стилевым сигналом остаются character-specific микродиалоги.

### `character_weights`

Отдельная таблица 28 координат `W_character` для каждого персонажа. Статья задаёт механизм и примеры policy-весов, но не готовые 28 чисел для имён из этого демо, поэтому ниже используется явная приближённая инициализация, выведенная из описаний характеров. Шкала `W_character` ограничена диапазоном `[0, 1]`: `0` исключает вклад координаты, `1.0` означает её максимальное проявление в данном характере, а промежуточное значение ослабляет вклад. Характер ничего не усиливает выше исходного `S_t`; веса только различают вклад эмоций при выборе поля. Эти числа не меняют формулу статьи и могут изменяться отдельно от текстовой библиотеки `communication_styles`.

### `motivation_styles`

Персонажно-зависимые мотивационные микродиалоги с ключом `(character_id, level)`, где уровень принимает значения `-1, 0, 1, 2`. Для уровней `-1/1/2` хранится обычная пара `USER → ASSISTANT`; уровень `0` — пустая вставка. Пары задают краткий или развёрнутый режим и написаны в том же регистре, что и коммуникационные пары конкретного персонажа; общего мотивационного текста нет. У Ирис в конфигурации по умолчанию `motivation_level=0`, чтобы отдельно показать работу коммуникационного стиля без мотивационного блока.

Источник инициализации мотивационных строк — поле `motivation` в том же JSON-файле персонажа. После загрузки данные копируются в SQLite; во время ответа движок читает только строку с текущими `character_id` и уровнем.

### `memory_entities`

Словарь канонических сущностей и псевдонимов.

### `associative_memory`

Для пары `(character_id, entity_id)` хранится 28-мерный эмоциональный вектор и число встреч `encounters`.

## Порядок формирования контекста LLM

```text
system prompt
→ реальная история диалога
→ коммуникационный микродиалог выбранной эмоции
→ мотивационный микродиалог
→ текущее сообщение пользователя
→ локальная LLM
```

Скрытые микродиалоги не записываются в реальную историю. Ассоциативная память тоже не вставляется в prompt как факт: она только влияет на `S_t` и через него — на выбор стиля.

## Трассировка

Для каждого ответа программа показывает:

```text
U_t        — 28 scores Multi-Motions 28
E_t        — состояние агента
S_base     — состояние без памяти
A_t        — ассоциативный сигнал
S_t        — итоговое состояние выбора стиля
R_t        — S_t, умноженное на W_character
entities   — найденные сущности
style      — стиль персонажа
emotion    — выбранная координата из 28
communication microdialogue
motivation microdialogue
answer
memory update
```

Чтобы вывод не занимал несколько экранов, CLI показывает наиболее сильные координаты и помечает общую размерность `(28 dims)`.

## Быстрый запуск

Нужен Python 3.10–3.12.

### Windows

```powershell
py -3.11 -m venv .venv
.venv\Scripts\python -m pip install -r requirements.txt
.venv\Scripts\python download_model.py
.venv\Scripts\python app.py --compare --show-context
```

### Linux / macOS

```bash
python3 -m venv .venv
.venv/bin/python -m pip install -r requirements.txt
.venv/bin/python download_model.py
.venv/bin/python app.py --compare --show-context
```

`download_model.py` загружает обе модели:

```text
Qwen/Qwen2.5-3B-Instruct
proxy3d/multi-motions-28
```

После этого inference выполняется из локальных директорий `demo/models/...`.
В качестве базовой генеративной модели выбран 3B-вариант: он рассчитан на удержание нескольких стилевых сигналов и существенно легче 7B для переносимого demo. На CPU он будет работать медленнее; для комфортного запуска предпочтителен GPU.
Для генерации стиля включено sampling: `do_sample=True`, `temperature=0.7`, `top_p=0.9`, `top_k=50`. Температуру можно изменить через `--temperature`, но значения ниже `0.7` demo отклоняет.

## Сравнение трёх персонажей

```bash
python app.py --compare --message "Я боюсь опоздать на рейс. Что мне делать?" --show-context
```

Один и тот же `U_t` проходит через baseline и три полные конфигурации персонажей. В режиме `--compare` ассоциативная память отключена для всех ветвей, а baseline использует нейтральный system prompt. Это сравнение конфигураций продукта, а не чистый причинный A/B-тест, в котором менялось бы только наличие микродиалога: у персонажей различаются system prompt, `alpha`, стиль, `W_character` и мотивация.


## Демонстрация памяти

Можно не загружать Qwen и использовать test backend для генерации:

```bash
python app.py --backend echo --memory-demo
```

Важно: `--backend echo` заменяет только генеративную LLM. **Multi-Motions 28 всё равно используется для `U_t`**, поэтому перед первым запуском `download_model.py` нужен и для этого режима.

Сценарий:

1. очищает память выбранного персонажа;
2. несколько раз подаёт сообщения о страхе полёта;
3. записывает эмоциональную ассоциацию с `самолет`;
4. затем подаёт более нейтральное сообщение:

```text
Завтра летим на самолете в Париж.
```

Сравните `S_base` и `S_t`: если память накопила fear/nervousness, `A_t` сдвигает итоговое состояние даже при более спокойном текущем `U_t`.

## Структура проекта

- `app.py` — CLI, сравнение персонажей, память и трассировка;
- `style_demo/emotion_classifier.py` — локальная обёртка над `proxy3d/multi-motions-28`;
- `style_demo/emotion.py` — 28 координат, `E_t`, `S_base`, `S_t`;
- `style_demo/dialogues/*.json` — авторские коммуникационные и мотивационные пары каждого персонажа;
- `style_demo/default_styles.py` — загрузчик JSON и структурная проверка, без текстовых шаблонов;
- `style_demo/db.py` — SQLite, связи персонажей со своими стилями, W_character и ассоциации;
- `style_demo/association.py` — нормализация сущностей и вычисление `A_t`;
- `style_demo/engine.py` — общий цикл classifier → memory → style → microdialogue → LLM;
- `style_demo/local_llm.py` — локальная генерация через Transformers;
- `download_model.py` — однократная загрузка обеих моделей;
- `tests/` — offline unit-тесты без скачивания весов.

## Что намеренно упрощено

Чтобы пример оставался читаемым, здесь пока нет:

- полноценного NER вместо словаря + `pymorphy3`;
- контекстных ассоциаций `(Entity, Context) -> Emotion`;
- embedding retrieval сущностей;
- полноценной модели динамики `E_t`;
- TTS;
- веб-сервера.

Классификацию пользовательских эмоций выполняет опубликованная **Multi-Motions 28** непосредственно; перечисленные выше упрощения относятся к другим компонентам учебного контура.

## Инициализация персонажей и примеры микродиалогов

Ниже собраны значения, с которыми создаётся база демо. Таблица характеров отделена от `communication_styles`: в последней хранятся только пары `USER → ASSISTANT`, а `W_character` — отдельная 28-координатная таблица. Числа являются приближённой policy-инициализацией для описанных персонажей, а не дополнительной формулой статьи: текстовое описание задаёт направление профиля, а значения делают это направление явным для селектора.

### Характеры

| Персонаж | Стиль (`style_id`) | Поведение | `alpha` | Интенсивность | Мотивация | Инициализация `W_character` |
|---|---|---|---:|---:|---:|---|

### Мотивационные микродиалоги по персонажам

Мотивация также хранится как законченные пары `USER → ASSISTANT`, отдельно для каждого персонажа и каждого уровня. Нулевой уровень — пустая вставка; у Ирис он выбран по умолчанию, поэтому её пример показывает только коммуникационный стиль. Уровень `1` задаёт краткость, `2` — развёрнутый ответ, `-1` — остановку или сокращение разговора; все три пары сохраняют регистр персонажа.

| Персонаж | `-1` · сокращение | `0` · без мотивационного блока | `1` · краткость | `2` · развёрнутый ответ |
|---|---|---|---|---|
| **Мира** | **USER:** Я устал, можно не продолжать разговор.<br>**ASSISTANT:** Понимаю. Не буду давить и помогу спокойно завершить мысль. | — | **USER:** Мира, ответьте коротко, пожалуйста.<br>**ASSISTANT:** Конечно. Отвечу кратко и бережно — мне приятно быть вам полезной. | **USER:** Мира, расскажите подробнее, если готовы.<br>**ASSISTANT:** С радостью. Дам полный ответ и аккуратно разберу детали. |
| **Алекс** | **USER:** Бро, не растягивай, можно свернуть разговор.<br>**ASSISTANT:** Понял, чувак. Коротко закрою тему без лишнего. | — | **USER:** Бро, ответь коротко, без лишнего базара.<br>**ASSISTANT:** Без проблем, чувак. ## Фактический пример запуска

Ниже приведены сокращённые фрагменты фактического вывода команды:

```bash
python app.py --compare --show-context \
  --message "Я боюсь опоздать на рейс. Что мне делать?"
```

### Тревожное сообщение

Для одного и того же входа Multi-Motions 28 дал:

```text
U_t: fear=0.80, nervousness=0.76
```

Память в `--compare` отключена, поэтому `A_t=0`. Все ветки выбрали поле `fear`, но значения `R_t = S_t ⊙ W_character` различались:

| Ветка | `S_base[fear]` | `R_t[fear]` | Коммуникационный уровень | Мотивация |
|---|---:|---:|---|---|
| Без стиля | `0.52` | `0.52` | нет | нет |
| Мира | `0.52` | `0.52` | `fear`, уровень `1` | `2`, развёрнутый ответ |
| Алекс | `0.48` | `0.41` | `fear`, уровень `1` | `1`, краткий ответ |
| Ирис | `0.56` | `0.39` | `fear`, уровень `1` | `0`, отключена |

Пример полного контекста Алекса перед генерацией:

```text
SYSTEM: Ты — точный собеседник в прямой уличной манере. ...
       уместно используй «бро», «чувак», «без базара» и «по факту».
USER: Бро, я боюсь, что всё пойдёт наперекосяк.
ASSISTANT: Слышу, чувак. Не кипишуй, разложим безопасный шаг.
USER: Бро, ответь коротко, без лишнего базара.
ASSISTANT: Без проблем, чувак. Дам короткий ответ по факту.
USER: Я боюсь опоздать на рейс. Что мне делать?
```

Фактические ответы в этом запуске:

```text
Без стиля:
Если вы боитесь опоздать на рейс, есть несколько шагов, которые можно предпринять: ...

Мира:
Если вас беспокоит опоздание на рейс, есть несколько вещей, которые вы можете сделать: ...

Алекс:
Бро, проверь время и маршрут ещё раз. Если опоздание ощутимо, возьми такси
или попроси друзей помочь тебе добраться до аэропорта.

Ирис:
Вот что могу предложить: проверь время еще раз, поищи информацию о времени
вылета на официальном сайте авиакомпании или их мобильном приложении. Если есть
возможность, звони службе поддержки для уточнения информации. Главное — успеть заранее.
```

Здесь видно разделение ответственности: классификатор выбирает эмоциональное поле, `W_character` участвует в выборе, таблица даёт характерную пару, мотивация меняет объём ответа, а реальное сообщение пользователя остаётся последним `USER` перед LLM.

### Нейтральное сообщение

Для входа `Привет` классификатор выбрал:

```text
U_t: neutral=0.91
Выбрано поле: neutral
```

Нейтральное поле не удаляет стиль. Оно также получает собственную пару персонажа:

| Персонаж | Нейтральная коммуникационная пара | Ответ модели |
|---|---|---|
| Без стиля | не добавляется | `Здравствуйте! Как могу помочь?` |
| Мира | `Есть задача, хочу понять факты.` → `Давайте разложим всё по порядку — мне приятно работать с вами.` | `Здравствуйте! Как я могу вам помочь сегодня?` |
| Алекс | `Чувак, давай разложим эту тему.` → `Без проблем, бро. Сначала факты, потом решение.` | `Привет, бро. Как дела?` |
| Ирис | `Давайте без душнилова разложим эту тему.` → `Вайб принят: факты, связки, нормальный вывод.` | `Рил, вайб! Приветствую! Как дела?` |

У Миры в этом примере добавляется мотивация уровня `2`, у Алекса — уровня `1`, а у Ирис уровень `0`, поэтому её контекст содержит только коммуникационную пару и реальный запрос. Это и есть результат, который пользователь видит при запуске `--compare --show-context`.
